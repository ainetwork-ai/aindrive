# Phone as a P2P media peer (Plan 5 of 6, scoped) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** While the aindrive app is open on a phone, a browser playing a video from
that phone's drive takes the chunks straight from the phone over WebRTC, verified. That
removes the server hop from the family's original problem (Grandma's phone video).

**Architecture:**
- **The split:** the native agent (Java/Swift) keeps the drive socket but has no WebRTC stack. The app's WebView does have one.
- **Native side:** on a `{type:"rtc"}` frame from the server, the native agent hands the frame to the WebView (a plugin event). The WebView replies through the plugin (`rtcSend`), and the agent sends that over the socket.
- **WebView side:** it checks the token with the drive secret it already holds, answers with `RTCPeerConnection`, and reads chunks through the plugin (`readChunk`, `statFile`).
- **Shared code:** the logic is the CLI's `media-rtc.js` behaviour (≤8 sessions, one chunk at a time, stat check, expiry), written once against injectable dependencies.

**Scope ruling:** phones are not yet Willow document peers. The browser and the server
already give phone drives offline editing and signed authorship, and browsers keep
saving files for agents without the "willow" capability. So this plan does only the
P2P media half. When the app is backgrounded the WebView sleeps; the server cache serves.

## Global Constraints
- Same wire, token and limits as Plan 7 (16 KiB pieces; ≤ 8 sessions; one chunk at a time; stat check; expiry per chunk).
- `mobile/` stays independent: the shared P2P code arrives as a generated TypeScript copy (`mobile/src/willow-shared/`), drift-tested like the CLI copy.
- Native glue is small; Android is compiled with javac + android.jar, iOS is unverified here (no Swift toolchain) and says so.

### Task 1: generated TS copy for mobile + the phone P2P answerer (testable)
- The generator also writes `mobile/src/willow-shared/{bytes,p2p}.ts` (a TS copy with a GENERATED header). The drift test covers it.
- `mobile/src/p2p.ts`: `createPhoneRtc({ RTCPeerConnection, readChunk, statFile, send, drives: () => Map<driveId, secret>, now })` exposes `handle(driveId, frame)`, with the same rules as `cli/src/media-rtc.js`.
- Tests (vitest in mobile, with werift standing in for both ends' RTCPeerConnection): chunks served and verified; wrong path, no answer; expired, nothing; a 9th session, refused.

### Task 2: native glue
- Android: `AgentService` forwards `type == "rtc"` frames to a static listener set by `AindriveAgentPlugin` (event `rtc`). New plugin methods: `rtcSend({driveId, frame})`, `readChunk({driveId, path, offset, length})` → base64, `statFile({driveId, path})`.
- iOS: the same in `AgentCore.swift` / `AindriveAgentPlugin.swift`.
- `mobile/src/plugin.ts` types; `main.ts` wires `createPhoneRtc` at start.
- Verify: javac against android.jar (0 errors in the touched files).
